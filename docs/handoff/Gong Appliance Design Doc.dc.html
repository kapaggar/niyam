Gong appliance for Android

A phone or tablet, plugged in at the centre, rings the course gong and the morning doha on the correct wall-clock time for the correct course day — without internet — while staff manage schedule, audio route and Wi-Fi on its own screen.

01 — Goals & non-goals

What v1 must be true about

Goals

  • Correct gong at the correct wall-clock time for the correct course day, offline, with the screen off.
  • Never fire early. Never fire twice. Never blast a missed 04:00 at 04:10.
  • Silence beats a wrong gong — an untrusted clock suppresses automatic plays.
  • A non-technical server can answer "what day, what's next, is it healthy" from across the office.
  • Behavioural parity with the Pi daemon, verified by porting its tests — not a line-for-line Python port.

Non-goals (v1)

  • Deshna media server / fetch.php — future module, must not block v1.
  • Cloud accounts, fleet management, analytics SDKs, any PII.
  • LAN second-device admin. The engine is written behind an interface so an embedded HTTP layer is additive later; nothing is exposed in v1.
  • GPIO relay amp power. Amp is assumed always-on or BT-powered.
  • Migration from a live Pi database. Fresh install + seed + manual course entry.

03 — Runtime architecture

One process, one source of truth

The Pi's gongd maps to a single foreground service that owns the scheduler and the player. The UI is a client of it, never a peer — closing the activity changes nothing.

GongService · foreground, type=mediaPlayback · START_STICKY · boot receiver
SchedulerEngine
Day resolution · materialization · fired-guard · grace/missed · clock trust
PlayerEngine
Single-slot job queue · burst timing · route warm-up · Media3 ExoPlayer
Wake sources
setAlarmClock for the next occurrence · 30 s in-service heartbeat · TIME_SET/TIMEZONE_CHANGED/DATE_CHANGED receivers · WorkManager 15-min liveness re-arm
Store
Room over SQLite (WAL) · settings/state KV · play_log · seeded from bundled seed.sql
Compose UI (activity) — observes engine state flows, issues commands. Interface-identical to the Pi JSON API, so an embedded HTTP admin can be added later without touching the engine.

Decisions

DecisionChoiceWhy
Min SDK29 (Android 10)Scoped storage + SAF are uniform; LocalOnlyHotspot is dependable; covers recycled centre hardware. Target 35.
Wake mechanismsetAlarmClockExempt from Doze and, unlike setExactAndAllowWhileIdle, not throttled to one per 9 min. Cost: it surfaces a system alarm icon — acceptable on an appliance.
Exact-alarm permissionRequest USE_EXACT_ALARMThe app's core function is an alarm clock, which is a permitted Play use of the non-revocable permission. Fallback if refused in review: SCHEDULE_EXACT_ALARM + first-run grant, plus the heartbeat.
Belt and bracesHeartbeat, alwaysThe service holds a 30 s loop even when alarms are armed; alarms are an optimisation, not the only path. This is how OEM killers get survived.
UI toolkitCompose, single activityNo webview of a Flask clone — the brief allows native, and a webview adds a second failure surface on the critical path.
DBRoom, no cloudField-repairable: the file is a plain SQLite DB an admin can pull over USB.
04 — Data model

1:1 with the Pi daemon, three deltas

Entities course_types, courses, schedule_events, settings, state, play_log carry the Pi semantics unchanged, including seed IDs. Room entities, same column names, so a pulled DB is readable by Pi tooling.

DeltaWhat and why
+ media_slots(slot INTEGER PK 1..11, uri TEXT, filename TEXT, source TEXT, verified_at). The Pi's manifest.json becomes a table because Android holds SAF document URIs, not paths, and staff need per-slot override. The manifest file remains the import/export format.
relay_enabled retained, inertKept in settings for parity and forward use (smart plug / USB accessory). Hidden in UI, always 0.
+ state.route_last_okRecords the last audio route that successfully rendered a fire, so a missing route at fire time is a diagnosable event rather than silence.

Unchanged and non-negotiable: start_date is day 0 (arrival); current_day is a calendar-date difference, never /86400; active course is the window match start_date ≤ today ≤ start_date + total_days, so a course that began while the device was off is still found.

05 — Scheduler state machine

Six states, one guarded transition

BOOT
Load state, compare now to last_good_time
RESOLVE
Active course, current_day
MATERIALIZE
Rows for date D + synthetic doha
ARMED
Alarm set for next; heartbeat running
FIRING
Guard written, job enqueued
CLOCK_UNTRUSTED
Automatic plays suppressed, tests allowed
RuleBehaviour
Fire windowfire_at ≤ now ≤ fire_at + 120 s. Outside it and unfired, log missed and move on.
Double-fire guardstate["fired:<key>:<date>"] is committed before the job is enqueued, in the same transaction that reads it.
Re-materialize onBoot · local midnight · course or settings change · TIME_SET/TIMEZONE_CHANGED · any heartbeat that observes a >120 s clock jump.
Clock trustlast_good_time written every 60 s. If now < last_good_time − 10 min on start → untrusted; automatic fires log skipped_clock; cleared by a forward NTP step or an explicit staff confirmation.
DSTDay math on LocalDate. Spring-forward gap → first valid instant after. Fall-back ambiguity → the first occurrence only.
Doha slotlegacy_modular ported verbatim (slots 1–11, metta and homage overrides last). Outside a course, no_course_doha = random | off | slot:n. Missing slot → skip + error log, never a crash.
06 — Audio

One route abstraction, four implementations

ConcernDecision
Route modelAudioRoute { Speaker, Bluetooth(deviceId), UsbDac(deviceId), WiredAmp } resolved against AudioDeviceInfo at fire time. Adding the wired amp in v1.1 is a new case, not a rewrite.
AttributesUSAGE_MEDIA + CONTENT_TYPE_SONIFICATION, not USAGE_ALARM — alarm usage is routed to the speaker on many OEMs even when BT is connected, which is exactly the failure we cannot have.
VolumeTwo app-level gains (gong_volume, doha_volume) applied as ExoPlayer volume; system media volume is pinned to max on first run with a note that it is a multiplier, not a substitute.
Burst timingPlayer prepared and route warmed 15 s before fire_at. Strikes scheduled on elapsedRealtime deadlines, not sleep(). Over A2DP the codec adds a constant 120–250 ms offset — constant, so the rhythm survives; the burst simply starts late. Documented, not fought.
QueueNew gong aborts the running burst. Doha waits for a running gong — never preempts. Stop aborts the current job only.
Route missing at firePlay on the fallback route (speaker) and log error with the intended route. A gong from the wrong speaker beats no gong; a silent failure is the one thing we refuse.
07 — Media & distribution

The APK ships gongs. Doha arrives by hand.

  • Play build bundles only the gong stems (ting, drum, …) in res/raw. No doha masters in the store artifact, so VRI rights are never a distribution question.
  • First run asks staff to grant a SAF tree on a folder — recommended /sdcard/DhammaGong/doha, shown as a literal path in the UI. The app persists the tree URI and watches it.
  • Files auto-map by D01…D11 filename prefix into media_slots; a mapping table shows slot → file with a per-slot override and a play button. Unmatched files are listed as "unassigned", never guessed at.
  • Doha with 0 slots filled is not an error state — the dashboard carries an amber gongs only chip and the gong schedule runs untouched.
  • Optional signed centre edition APK, same code, media pack pre-seeded, for centres that cannot use Play.

Six, each justified in the Play listing

PermissionWhenJustification / risk
USE_EXACT_ALARMManifestAlarm-clock function. Non-revocable but policy-reviewed — the listing must state the app is a scheduled alarm device. Risk: rejection; fallback is the revocable variant.
FOREGROUND_SERVICE_MEDIA_PLAYBACKManifestScheduled audio playback with the screen off. specialUse avoided — it draws more scrutiny than mediaPlayback here.
POST_NOTIFICATIONSFirst runThe persistent status notification is the appliance's health indicator. Denied → service still runs, health is visible only in-app.
RECEIVE_BOOT_COMPLETEDManifestPower loss recovery.
BLUETOOTH_CONNECTOn route pickOnly when the user chooses a BT route.
Battery optimisation exemptFirst runNot a permission — an intent. OEM variance is high; the checklist links per-OEM instructions and verifies by observing a heartbeat over 20 min.
10 — Failure matrix

What happens when

EventBehaviour
Power cut, restored 03:59:50Boot receiver → RESOLVE → 04:00 fires normally inside grace.
Power cut, restored 04:10missed logged, nothing plays, dashboard shows the miss until acknowledged.
Process killed mid-burstGuard already written → no repeat on restart. play_log result stays stopped.
Clock jumps backwards 6 hUntrusted → automatic plays log skipped_clock, amber banner, tests still work.
Clock corrected forward by NTPTrust restored, re-materialize; anything now outside grace is missed, not fired.
Airplane mode, no network, foreverFully operational. Network is used for nothing on the critical path.
BT amp not connected at fireSpeaker fallback + error log + dashboard route warning.
Two overlapping course windowsMost recent start_date wins, dashboard warns and offers the override.
Device unplugged, battery diesNothing fires. On restore, boot path applies; the dashboard shows the outage span.

12 — Test plan

No hall required until M4

  • Unit (JVM). Pi's test_scheduler, test_doha, test_player ported as the oracle. Every legacy bug from §3.1 gets a named regression test — the day-2 fallback, the 0 => 0 doha index, the /86400 DST break.
  • Virtual clock. The engine takes an injected Clock; a 400-day run over every course type executes in seconds and asserts an exact fire ledger.
  • Instrumented. Doze forced via adb, alarm-permission denial, force-stop mid-burst, timezone flip, DST boundary dates, BT disconnect at fire time.
  • Field. A compressed-time mode (1 course day per 20 min) so a full 10-day course is observable in a single afternoon on a desk.

14 — Unresolved

Six questions, ranked

  1. Which tablet model(s) will centres actually buy? OEM battery behaviour is the top risk and it is model-specific.
  2. Is the system alarm icon from setAlarmClock acceptable on a wall tablet, or does it need the throttled path?
  3. Does any centre need two schedules on one device (two halls)? Assumed no; it changes the data model if yes.
  4. Who signs and hosts the centre-edition APK, and how do centres verify it?
  5. Is kiosk / screen-pinning first-class in v1, or a documented device-owner setup step?
  6. Hindi at launch or after? It is cheap now and expensive to retrofit into a grid layout later.
